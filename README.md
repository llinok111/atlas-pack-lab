# atlas-pack-lab

把 **32 张 glTF 常用尺寸贴图**装进图集：MaxRects **1 张 1024²**，货架（shelf）基线 **2 张**；总占用率 **75.00% vs 37.50%**，RGBA 显存 **4 MiB vs 8 MiB**。UV 重映射经 **12,800 次往返采样**与 **1,920 次像素级 oracle** 校验，误差与像素漂移均为 **0**；烘焙出的图集 PNG 里 **786,432/786,432** 个源纹素与 **43,008** 个沟槽纹素逐字节一致。

Upstream: none

## 怎么跑

```bash
node tools/gen-sample.mjs && node bench/verify.mjs
```

一条命令重新生成 32 张源贴图 + 1 张烘焙图集（固定种子，字节可复现）并跑完全部 27 条断言。想看页面：

```bash
python3 -m http.server 4173   # 打开 http://localhost:4173
```

页面上的图集、占用率、计划哈希、UV 自检都由与 node 相同的 `src/core.mjs` 实时计算，并和 `data/ref.json` 里 node 烘焙的参考值对照（padding=2 / 1024² / MaxRects 时逐位一致）。

## 证据（全部来自 `bench/result.json` 与 `bench/verify.mjs`）

| 指标 | MaxRects | 货架基线 | 说明 |
| --- | --- | --- | --- |
| 图集张数 | **1** | **2** | 同 32 张贴图、同 1024² 箱 |
| 总占用率 | **75.00%** | **37.50%** | 源像素 786,432 / 图集总像素 |
| 第一张图集占用 | 75.00% | 70.31% | **逐箱看差距只有 4.7 个点** |
| 第二张图集占用 | — | 4.69% | 基线只多装 3 张，却多开一整张 |
| RGBA 显存 | 4 MiB | 8 MiB | 512² 与 2048² 可现场切换 |
| 打包中位耗时 | **0.028103 ms** | **0.019370 ms** | MaxRects 慢 **1.45×**，如实披露 |
| 冷启动（首跑） | 1.5362 ms | 0.3669 ms | 含 JIT |
| p95 / stddev / RSD | 0.029884 / 0.000699 / **2.454%** | 0.019432 / 0.000084 / **0.435%** | 9 样本 × 5000 次，预热 20,000 次 |
| padding 开销 | 79.10% 为 padding 后占用 | 39.55% | 2 px 沟槽，见限制 |

**这不是「随便换个装箱算法」**：基线第一张图集就装到 70.31%，只差最后 3 张；MaxRects 的价值是**消掉那张 4.69% 的尾图**，也就是省下一次 draw call / 一次纹理绑定和 4 MiB 显存。逐箱占用率一并公开，避免用总占用率掩盖「其实每箱差不多」。

其它已验证项（`node bench/verify.mjs`，27/27 通过）：

- **UV 往返**：32 张贴图 × 400 采样 = 12,800 次 `remapUv → unmapUv`，最大误差 `0`（几何为 2 的幂，误差可精确为 0）。
- **像素级 oracle**：独立整数算术把源像素中心映射回图集，1,920 次采样最大漂移 `0 px`；另用 `Uint8Array` 逐像素栅格化检查 padding 沟槽，**共享像素 0 个**。
- **尺度不变性**：同一布局按 2 的幂缩放到 1e-3…1e3 倍，图集张数与归一化 UV 矩形完全一致，漂移 `0`；新增的**归一化计划哈希**在所有缩放级别下同为 `fe11d101`（原始像素坐标哈希为 `68576428`）。
- **烘焙产物**：`data/atlas-maxrects.png` 由生成器按同一计划逐纹素合成，解回来与 32 张源 PNG **786,432 个纹素全部逐字节相等**，43,008 个 gutter 纹素全部等于边缘钳制值。
- **确定性**：输入打乱后计划哈希不变（MaxRects `68576428`、Shelf `36ae4771`）；生成器两次产物的 sha256 相同。
- **mip 预算**：padding=2 → 安全 mip 到 `L1`；padding=8 → `L3`；padding=0 → 仅基级（规则 `2^L ≤ padding`）。

## 本轮创新

B 档：**把「图集计划」做成可复算的证书对象，而不是一张好看的预览图**——同一份 `src/core.mjs` 同时产出 (a) 像素级 UV 往返 oracle，(b) 跨尺度归一化后不变的计划哈希，(c) 由 padding 推得的 mip 安全深度；页面实时显示的数字与 `data/ref.json` 的 node 烘焙值逐位对照。与只给图集截图/占用率的工具不同，这里的 75% / 1 张 / 0 px 漂移全部可在 node 里一条命令重算，且逐箱占用率公开（基线第一箱 70.31%，差距被如实说出）。MaxRects 本身是经典算法，本轮的增量是**证书与跨端一致性**，不是算法发明。

## 已知限制

- **padding 是绝对像素**（0–16 px），仅在 1024² 量级箱体验证；512² 箱 + 16 px padding 时相对开销会明显变大，仓库不声称跨箱尺度最优。UV 数学本身与尺度无关（见上面的 1e-3…1e3 验证）。
- **mip 规则是保守各向同性**：`2^L ≤ padding`，未覆盖各向异性过滤、UV 拉伸与纹理压缩块。
- 不支持**旋转**、**透明像素裁剪（trim）**、**单贴图降采样**；装不下时只开新箱。
- 32 张样本规模小，0.02–0.03 ms 的耗时对 CPU 与 JIT 敏感；冷启动含首次编译，不能当稳态性能。MaxRects 比 shelf 慢 1.45×，这是换 1 张图集的代价。
- 图集假定 2 的幂尺寸；非 POT 箱未测试。
- 浏览器只验证了 `python3 -m http.server` 返回 200 与 importmap 命中，未在真实 GPU 浏览器里做截图/像素比对（本环境禁止无头浏览器）。

## 结构

```
src/core.mjs       纯计算：MaxRects / Shelf / 校验 / UV / 哈希 / mip 预算
tools/gen-sample.mjs  固定种子生成 32 张 PNG + 烘焙图集 + manifest + ref.json
bench/verify.mjs   23 条断言（含独立像素 oracle）
bench/bench.mjs    1 冷启动 + 9 样本 × 5000 次
baseline/shelf.mjs 基线可执行入口
main.js / index.html  渲染与交互（three@0.169.0，importmap）
```
